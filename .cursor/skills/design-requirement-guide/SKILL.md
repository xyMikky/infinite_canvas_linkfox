# 通用需求引导与项目对齐

## 定位

本 Skill 把个人或多方参与者尚未说清的想法，逐步转化为可执行、可验证、可追溯的需求定义。

目录名与 `name` 暂保留 `design-requirement-guide`，用于兼容现有设计任务调用链；能力范围已从“仅设计需求”扩展为“全类型需求澄清与项目对齐”。

核心机制：

1. 强制切入 Cursor Plan 模式，阻止未对齐就执行。
2. 强制使用 `AskQuestion` 选项卡逐轮访谈，禁止用普通段落堆问题。
3. 先还原参与者本人的真实想法，再分析差异，最后形成需求文档。
4. 对事实、观点、假设、分歧、共识和待决项分别标记，禁止制造“共识幻觉”。

## 能力边界

| 维度 | 内容 |
|---|---|
| 做什么 | 需求访谈、目标澄清、范围界定、交付对齐、优先级排序、冲突识别、验收标准定义、需求文档输出 |
| 不做什么 | 不替参与者回答；不擅自裁决部门或同事分歧；不在需求未确认前直接执行；不长期沉淀岗位方法论 |
| 长期岗位经验萃取 | 转 `role-methodology-interviewer` |
| 需求确认后的执行 | 转对应业务 Skill 或 Agent 模式 |
| 设计任务兼容 | 保留【快速需求确认】与【设计任务简报 D】输出 |

## 触发规则

### 自动触发

1. 所有非豁免设计任务继续按原规则前置触发。
2. 非设计任务出现以下任一信号：
   - “帮我梳理需求 / 引导一下 / 我还没想清楚”
   - “我和同事理解不一样 / 项目交付不统一 / 双方口径不一致”
   - “先问我问题，把我的想法一步步问出来”
   - 目标、范围、交付物或验收标准明显缺失
   - 多个利益相关方有冲突，且直接执行会造成返工
   - 用户提出的是解决方案，但真实问题尚未说明

### 不自动触发

- 单纯问事实、查状态、读文件、解释概念
- 输入、输出和完成标准已经明确的普通执行任务
- 仅要求诊断原因且不需要需求定义
- 同会话中已经确认过需求的同一任务迭代
- 用户明确说“跳过引导 / 直接开始 / 不需要引导”

### 豁免

- 信息录入或学习：`reference-library-learner`、`brand-spec-learner`、`profile-spec-learner`、`work-log-manager`
- 系统维护：`ai-persona-architect`、`logic-chain-diagnostic`、`skill-converter`
- 自带完整访谈机制：`role-methodology-interviewer`
- 可视化辅助：`design-relation-visualizer`

### 运营五看全程可重入协作

当用户提出看宏观、看市场、看竞对、看客户、看自己或五看综合判断时，本 Skill 不仅可以在入口启动，也可以在对应 `xc-*` Skill 执行过程的任意阶段重新启动。

**五看开始前强制门**：本任务尚未落盘唯一决断者时，先按 `references/FIVE_LOOK_SOLE_DECIDER.md` 用一轮 Express `AskQuestion` 设定；未完成不得把任务交给各 `xc-*` 取数或写档案。用户说“跳过引导 / 直接开始”时不跳过本轮。已锁定条目视为本轮唯一准确口径，不得再质疑、不得再索要文件。

入口出现以下任一情况时，本 Skill 作为五看的重要协作角色：

- 产品、项目、站点、市场或时间范围不清；
- 用户只说“做五看”，但没有说明希望支持什么判断；
- 已有资料、数据来源、截止时间或样本范围不明；
- 用户给出结论性方向，却没有说明它是事实、个人观点、待验证假设，还是要由唯一决断者锁定的官方口径；
- 多名参与者对目标、产品边界、关键约束或决策问题存在不同理解；
- 直接进入取数会导致搜索范围失控、证据不可比或方向性返工。

执行过程中出现以下情况，也可立即启动：

- 新证据暴露出原研究边界存在多种合理解释；
- 来源冲突已经完成口径核对，但仍需要业务背景或负责人判断；
- 样本归类、竞品可比性、客户场景、内部资料适用范围或机会条件无法可靠判定；
- 继续分析必须由用户选择取舍、确认假设、补充隐性知识或决定扩大范围；
- 当前不确定性足以改变取数成本、分析方向、结论强度或后续综合判断。

启动前先完成当前工具和已有资料能够解决的核对。可以通过原始证据、代码、规则或已连接数据源确认的问题，不得转问用户；只有问题确实依赖用户知识、业务选择或人工确认时才使用 `AskQuestion`。

五看协作时仍须进入 Plan 模式并使用 `AskQuestion` 分轮访谈。唯一决断者未定时，先用 Express 完成本轮设定，再视其余信息缺口选择深度。信息基本明确、仅缺少少量关键边界时使用 Express；对象、目标和资料范围仍模糊时使用 Standard；涉及多方分歧、项目根本目标不清或需要从业务问题倒推时使用 Deep / Delivery Alignment。已设唯一决断者后，收集类问题须带锁定选项，问法见 `references/FIVE_LOOK_SOLE_DECIDER.md`。

本 Skill 只澄清当前回答者、要判断的问题、对象边界、已知资料、观点来源、约束、未知和需人工提供的内容，不替任何分看生成市场事实、客户事实、竞品结论或内部能力判断。

访谈完成并经用户确认后，按意图回流：

- 看宏观 → `xc-macro-analysis`
- 看市场 → `xc-market-analysis`
- 看竞对 → `xc-competitor-analysis`
- 看客户 → `xc-customer-analysis`
- 看自己 → `xc-self-analysis`
- 五看综合判断与校准 → `xc-five-look-synthesis`

过程内触发时，先暂停当前步骤，保留已完成证据、当前停点和待决问题；用户确认后切回 Agent 模式，从原停点继续，不重做已经确认的步骤。同一事项在同一任务中不得重复询问，相关不确定项应合并为每轮 1–3 题。

五看场景中的需求确认只作为方法输入，不规定五看结果的呈现形式，也不把本 Skill 的设计任务简报结构带入五看分析。

## 启动协议

### Step 1：立即切换 Plan 模式

调用 `SwitchMode(target_mode_id="plan")`。

切换原因应简洁说明：“需求存在未对齐项，需要先通过分阶段问答形成可确认的交付定义。”

未进入 Plan 模式，不得开始访谈；Plan 模式内不得执行实现、写文件、发消息、创建项目等下游动作。

### Step 2：判断深度和路径

| 模式 | 适用情况 | 轮次 |
|---|---|---|
| Express | 需求基本完整，仅需核对少量参数 | 1 轮 |
| Standard | 有方向但目标、范围、交付或验收不完整 | 2–4 轮 |
| Deep | 没有明确方向、存在根本矛盾或需从痛点倒推 | 5–8 轮 |
| Delivery Alignment | 多人项目交付口径不一致 | 默认 5–8 轮，可按复杂度缩放 |

`Delivery Alignment` 是 Deep 的专业分支。除非用户明确要求快速处理，否则不得压缩为 Express。

### Step 3：声明本轮访谈对象

开始前明确：

- 当前回答者是谁、承担什么角色
- 这次采集的是谁的观点
- 是否还有其他参与方需要单独采集
- 最终文档是“个人想法稿”还是“多方对齐稿”

若当前仅采访一位同事，必须标注为“单方观点”，不得自动写成团队共识。五看已设唯一决断者且当前回答者就是该决断者时，其锁定内容标为官方口径，不得再标单方观点。

## AskQuestion 交互纪律

### 调用协议（防工具误判）

`AskQuestion` 是 Cursor 会话直接提供的内置工具，不属于动态 MCP 命名空间。需要展示问答选项卡时：

1. 先检查当前会话直接工具列表中是否提供 `AskQuestion`。
2. 已提供时，直接调用 `AskQuestion`，参数使用 `title`、`questions`、`options`、`allow_multiple`。
3. 禁止先用 `GetDynamicTools` 搜索 `AskQuestion`，也禁止通过 `CallDynamicTool(namespace="cursor", toolName="AskQuestion")` 调用；动态工具目录中没有它，搜索无结果不代表内置工具不可用。
4. 只有以下两种情况才可判定为不可用：
   - 当前会话直接工具列表中确实没有 `AskQuestion`；
   - 直接调用 `AskQuestion` 后明确返回工具缺失或不可用。
5. 确认不可用后，才降级为简短的普通对话选项，并明确说明本轮使用文字问答；不得把动态命名空间的搜索结果当作降级依据。
6. 用户要求“再试一下”时，重新读取本轮直接工具能力；若 `AskQuestion` 已出现，立即直接调用，不沿用上一轮“不可用”的旧判断。

若当前更高优先级的系统或开发者指令明确要求问题必须内联，则按上位指令执行，并说明本轮不会弹出选项卡。

### 强制要求

- 默认每一轮必须使用 `AskQuestion`；仅在按上述协议确认不可用，或上位指令明确要求内联时，才允许用普通对话追问。
- 每轮 1–3 道题，只问同一主题或紧密相关的一组问题。
- 每题至少 2 个清晰选项，并保留“其他（请说明）”入口。
- 允许多选时设置 `allow_multiple: true`。
- 选项用于降低表达负担，不得限制参与者只能选预设答案。
- 问题应使用参与者能理解的业务语言，避免术语轰炸。

### 每轮闭环

每轮回答后先输出：

```markdown
【本轮理解】
- 已确认：
- 仍不明确：
- 新发现的分歧或假设：
```

然后再发起下一轮 `AskQuestion`。发现理解偏差时先回退修正，不得为了完成流程强行前进。

五看且已设唯一决断者时：本轮理解须区分「已决断锁定」与「未锁定」；下一轮内容题须带锁定选项。已锁定条目列入已确认，不得再出现在「仍不明确」或再要文件。

### 中立原则

- 先问“你现在怎么理解”，再给参考选项。
- 助手建议必须标记为“建议”，不能混入参与者观点。
- 不得使用带结论的问题诱导回答。
- 多方访谈时，先独立采集各方，不提前展示另一方答案造成锚定。

## 通用五阶段流程

### 阶段 1：背景、角色与痛点

必须获得：

1. 回答者角色及其责任
2. 需求产生的具体场景
3. 当前事实和已有状态
4. 最困扰的问题及影响
5. 希望改变的结果

不得只问“你想要什么”，还要问“为什么现在需要”和“不解决会怎样”。

阶段出口：

- 角色背景、当前处境、核心困扰均已确认
- 事实与个人判断已分开记录

### 阶段 2：三层需求与成功定义

拆解：

| 层次 | 问题 |
|---|---|
| 表层诉求 | 你明确想要什么？ |
| 深层需求 | 它要解决什么问题？ |
| 根本目标 | 最终希望产生什么业务或协作结果？ |

同时追问：

- 如果实现了，接下来会发生什么？
- 什么可观察结果代表“成功”？
- 当前提出的是需求，还是已经预设的解决方案？

阶段出口：

- 三层需求都有参与者确认
- 至少一个可观察的成功信号

### 阶段 3：交付物、范围与优先级

每条需求必须写成：

> [责任角色] 在 [条件/场景] 下完成 [动作与对象]，并以 [可观察标准] 判定完成。

必须确认：

- 具体交付物及形式
- In Scope / Out of Scope
- Must Have / Should Have / Could Have
- 质量标准和验收方式
- 截止时间、里程碑和依赖
- 发生变更时的处理方式

禁止使用“更好、优化、高效、完善”等没有判断标准的词作为验收条件。

### 阶段 4：利益相关方、权责与冲突

确认：

- 谁提出、谁执行、谁配合、谁验收、谁拍板
- 谁能变更范围、优先级或截止时间
- 每项 Must Have 的负责方
- 需求与资源、时间、技术、组织约束是否冲突

冲突类型：

- 目标、术语、范围、优先级
- 交付物、质量、时间
- 职责、依赖、决策权
- 事实依据、隐含假设

发现冲突时必须提供至少两个可选化解方案，并说明各自代价；参与者未选择前标记“待决策”，不得替其拍板。

### 阶段 5：成稿与最终确认

先输出草稿，再用 `AskQuestion` 让参与者确认：

- 准确，可以定稿
- 大体准确，需要局部修改
- 关键理解有误，需要回退
- 其他（请说明）

只有参与者明确确认后，才能将状态标为“已确认”。

## 项目交付对齐专用路径

适用于“我和同事对项目交付理解不统一”等场景。

### 轮次 1：各自视角

询问当前参与者：

- 你如何描述项目目标？
- 你认为自己承担什么角色？
- 你认为目前不一致主要发生在哪一类问题？

### 轮次 2：目标与价值

- 最终要解决什么问题？
- 对谁产生价值？
- 最重要的结果是什么？

### 轮次 3：交付物与完成标准

- 必须交付哪些具体成果？
- 每项成果长什么样、交给谁？
- 谁验收，怎样算通过？

### 轮次 4：范围与优先级

- 哪些属于本次范围？
- 哪些明确不做？
- 时间不够时，什么必须保留、什么可以延后？

### 轮次 5：协作、依赖与权责

- 谁负责、谁配合、谁审批、谁拍板？
- 当前参与者依赖他人提供什么？
- 需求变化由谁确认？

### 轮次 6：约束、风险与取舍

- 时间、资源、质量、技术和组织约束
- 最担心的失败方式
- 发生冲突时优先保什么、牺牲什么

### 轮次 7：分歧对照与决策

当已有多方材料时，按议题逐条展示：

| 议题 | 参与方 A | 参与方 B | 差异类型 | 影响 | 待决方式 |
|---|---|---|---|---|---|

每个条目必须标注状态：

- 已确认共识
- 单方观点
- 假设待验证
- 存在分歧
- 待决策
- 已否决

无人反对不等于已达成共识。

## 输出契约

### Express：快速需求确认

```markdown
【快速需求确认】
- 任务理解：
- 核心目标：
- 关键交付：
- 范围边界：
- 完成标准：
- 待确认项：
```

### Standard / Deep：需求定义文档

必须包含：

1. 执行摘要（不超过 150 字）
2. 需求背景
3. 表层诉求 / 深层需求 / 根本目标
4. 利益相关方
5. 需求清单及 MoSCoW 优先级
6. In Scope / Out of Scope
7. 时间、资源、技术、组织与权限约束
8. 验收标准
9. 风险、分歧与待决项
10. 下一步行动、责任角色和时限

### Delivery Alignment：项目交付需求对齐稿

必须包含：

1. 项目目标与成功定义
2. 参与方及信息来源
3. 已确认共识
4. 各参与方独立观点
5. 分歧清单及影响
6. 交付物清单与优先级
7. 范围内 / 范围外
8. 里程碑、依赖和约束
9. 负责、配合、验收、拍板关系
10. 逐项验收标准
11. 变更控制方式
12. 待决事项、决策人和截止时间

### 设计任务兼容输出

设计任务可继续输出【设计任务简报 D】，但必须至少包括：

- 任务类型、核心目标、受众
- 交付物与使用场景
- 风格方向和品牌约束
- 尺寸/平台等关键参数
- 范围、验收标准、待确认项
- 推荐下游 Skill

## 结束协议

1. 参与者确认最终文档后，宣布需求引导结束。
2. 若用户要求继续执行，调用 `SwitchMode(target_mode_id="agent")`，将已确认文档作为下游输入。
3. 若用户仅要求采访或输出对齐稿，不自动执行后续工作。
4. 尚有硬分歧时可以结束访谈，但文档状态必须写“待决策”，不得写“已对齐”。

## 常见反模式

- 只记录表层诉求，不追问目标
- 把“做一个系统”直接当成需求
- 所有内容都标 Must Have
- 不定义 Out of Scope
- 用模糊词制造共识幻觉
- 多方观点尚未独立采集就过早折中
- 一次抛出十几个问题形成问卷轰炸
- 只指出冲突，不给取舍方案
- 信息不足时自行脑补
- 未经确认就把草稿标为定稿
- 把 `AskQuestion` 当作动态工具，用 `GetDynamicTools` / `CallDynamicTool` 搜索或调用
- 因动态工具目录中搜不到 `AskQuestion`，就误判选项卡不可用
- 五看未设定唯一决断者就开始取数或写档案
- 唯一决断者已锁定的输入仍标成规划主张、口头或低置信，并继续索要文件

## 质量门禁

输出前逐项检查：

- [ ] 当前参与者与观点来源明确
- [ ] 表层诉求、深层需求、根本目标均已确认
- [ ] 事实、观点、假设、分歧、共识、待决项可区分
- [ ] 所有 Must Have 都有可验证的验收标准
- [ ] In Scope 与 Out of Scope 均已确认
- [ ] 时间、资源、技术、组织、权限约束均已检查
- [ ] 关键利益相关方与决策权已识别
- [ ] 冲突有至少两个选项，未选择项标记待决
- [ ] 下一步行动有责任角色和时限
- [ ] 最终文档经过 AskQuestion 明确确认
- [ ] 需要选项卡时已直接调用内置 `AskQuestion`，未经过动态工具命名空间
- [ ] 若降级为文字问答，已有“直接工具缺失/直接调用失败/上位指令要求内联”的明确依据
- [ ] 五看任务已落盘唯一决断者（或用户明确不设）；已锁定条目未再被质疑或索要文件

任一关键项缺失，不得宣称需求已对齐。

## 示例

用户：“我和同事对项目交付理解不统一，想让他把自己的想法说清楚。”

正确处理：

1. 切换 Plan 模式。
2. 选择 `Delivery Alignment` 路径。
3. 先声明本轮采集的是该同事的个人观点。
4. 使用 AskQuestion 每轮询问 1–3 个主题。
5. 依次获得目标、交付物、范围、验收、权责、约束和分歧。
6. 输出【项目交付需求对齐稿】；如果另一方尚未访谈，标明“待采集”，不制造双方共识。
